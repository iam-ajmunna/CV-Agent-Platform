# DATA CONTRACT

Derived from `[P§7]` (dataset engineering), `[P§26]`, `[P§27]`, `[P§29.5]`.

> Data is an engineering artifact, not an input file `[P§26]`.

## Non-negotiables

1. **Every dataset has a version and a manifest.** An experiment referencing a dataset
   without a version id is void `[P§25]`.
2. **Annotations are versioned independently of images.** Relabeling produces a new
   annotation version, never an in-place edit.
3. **Splits are recorded, not recomputed.** The exact train/val/test membership is part of
   the manifest. A split regenerated by a random seed at runtime is not reproducible.
4. **Dataset mutation is an approval-gated action** — delete, relabel, overwrite, re-split
   `[P§24]`. See `docs/APPROVALS.md`.

## Manifest fields

`dataset_id` · `version` · `created` · `source(s)` · `n_items` · `class definitions
(explicit, with edge-case rules)` · `class distribution` · `split membership (hashes or
explicit lists)` · `split policy` · `annotation_version` · `annotation guideline
reference` · `known issues` · `lineage (parent version + transformation)` · `license /
usage constraints` · `collection conditions (cameras, sites, times, lighting)`

## Leakage checks — run before every split is accepted `[P§26]`

| Leakage type | Check |
|---|---|
| **Temporal** | No two frames from the same video segment across splits. Time-ordered split for anything with motion. |
| **Camera** | A camera/site appearing in train must be absent from test if the goal is generalization to new cameras — state which goal applies. |
| **Near-duplicate** | Perceptual-hash sweep across splits. |
| **Subject / identity** | Same person, vehicle, or object instance not straddling splits for Re-ID or tracking tasks. |
| **Annotation-round** | Data labeled in one round with a different guideline is not mixed silently. |

The check result is recorded in the manifest. "We used a random split" is a finding, not
a method.

## Class definition discipline `[P§5]`, `[P§7]`

A class is not defined until its **edge cases** are written down. For an event class
(theft, escape attempt, wall climbing), the definition must state:

- what physically constitutes the event, in observable terms;
- when it starts and ends (temporal boundary);
- what near-misses are explicitly **negative**;
- what is ambiguous and how annotators must resolve it.

Ambiguous class definitions are the most common root cause found in failure analysis
`[P§27]`; they are cheaper to fix here than after training.

## Dataset design `[P§7]`

Consider and record decisions on: annotation strategy · class imbalance · **hard
negatives** · edge-case coverage · augmentation policy · synthetic data · active learning
loop · collection plan for what does not yet exist.

For CCTV specifically `[P§9]`: coverage across time of day, weather, occupancy, camera
angle, compression level, and camera health. A dataset from one week of one camera
predicts nothing.

## Versioning mechanism

Decided via Q10 resolution (`D-028`): **Manifest-first content-addressed dataset storage with pluggable payload backends.**

- **Authority:** Git-tracked dataset manifests define all metadata, split memberships, annotation references, and payload checksums.
- **Payload:** Raw image/video payloads are stored outside Git in a pluggable content-addressed object store (`local_fs`, `s3`, `gcs`, `minio`).
- **Dependencies:** Neither DVC nor Git LFS is a core runtime dependency. DVC compatibility may be provided later via an optional adapter.

### Required Invariants

1. **Immutable version:** Every dataset increment produces a unique, immutable version.
2. **Authoritative manifest:** Every dataset has a complete Git-tracked manifest.
3. **Content-addressed identity:** Dataset identity and item references derive from cryptographic content hashes.
4. **Independent annotations:** Annotation versions are decoupled from underlying media payloads.
5. **Explicit splits:** Split memberships are explicitly recorded lists/hashes, never dynamic seeds.
6. **Deterministic retrieval:** Any historical version is deterministically retrievable via its manifest and payload hashes `[P§29.5]`.
7. **Approval-gated mutation:** Dataset deletion, relabeling, overwriting, and re-splitting require human approval `[P§24]`.
8. **Audited leakage:** Leakage check results (temporal, camera, duplicate, identity, annotation round) are recorded in the manifest.
9. **Remote retrieval:** Remote GPU/cloud targets can fetch required payloads directly via content hashes without cloning full Git history.
10. **Git-diffable metadata:** All dataset metadata and manifests remain human-readable and Git-diffable.

## Dataset card

Each version ships a short card: what it contains, how it was collected, its intended
task, its known biases and gaps, and what it must **not** be used to claim.
